# Rule: Internationalisation (`src/libs/i18n/`)

Every user-facing string this API returns — response messages, error messages, mail subjects, validation messages — is a **catalog key**, not an English literal. The i18n layer is hand-rolled and lives entirely in `src/libs/i18n/`. There is no `nestjs-i18n` equivalent here and none is wanted.

This rule describes the **current** state of `clean-elysia`, not an aspiration: `src/modules/auth/index.ts`, `src/modules/auth/service.ts`, `src/modules/profile/index.ts`, `AuthMailService`, `ErrorHandlerPlugin`, **the three settings CRUD services, and all four settings modules' handlers** resolve their messages through `@i18n` — 87 catalog keys. Modules added later match that.

Every user-facing string on the HTTP surface is now a key. The four settings modules (`role`, `permission`, `user`, `select-option`) resolve their success messages through `trans(...)` in the handler (`ResponseToolkit.success(result, trans("role.listSuccess"), 200)`), and the thrown *errors* from those surfaces are translated from the **service** — see rule 6 under "Don't" below.

## The two entry points

`@i18n` exports exactly two translators.

```ts
import { t as trans } from "@i18n";

trans("profile.retrieved");
trans("auth.emailAlreadyRegistered", { email });
```

- `t(key, vars?)` resolves against the **current request locale**. Use it everywhere inside a request.
- `translate(key, vars?, locale?)` takes an explicit locale. Use it only where there is no request locale to read — a BullMQ worker, a seed script, a startup log line.

`key` is typed `TranslationKey`, so a typo or an unregistered key is a **compile error**, not a silent English fallback. Route files alias the import as `trans` because `t` is already Elysia's TypeBox namespace — keep that alias; services import plain `t`.

## Catalogs: two flat files, moved together

- `src/libs/i18n/locales/en.json` and `src/libs/i18n/locales/id.json`.
- Both are **flat** maps of dotted key to string — `"auth.invalidCredentials"`, `"validation.required"`, `"mail.subject.verification"`. There is no nesting; the dots are part of the key. Current groups: `common.`, `errors.`, `auth.`, `profile.`, `role.`, `permission.`, `user.`, `selectOption.`, `validation.`, `mail.`. The last three sets are named to match the sibling `clean-elysia-prisma`'s catalogue, so a key can be carried across without renaming.
- `DEFAULT_LOCALE` is `en` (`src/libs/i18n/types.ts`). It is the fallback both for an unsupported locale and for a key missing from a supported one.
- Interpolation is **double-brace**: `"Welcome, {{name}}"`, filled from `vars`. A placeholder with no matching var is left verbatim as `{{name}}` — visible in the response, which is the point.

**`en` and `id` move together.** A key added to one is added to the other in the same change. This is enforced, not merely asked: `bun run i18n:keys` exits non-zero when `id.json` is missing a key that `en.json` has.

## `keys.generated.ts` is generated

`src/libs/i18n/locales/keys.generated.ts` declares the `TranslationKey` union and is written by `src/libs/i18n/scripts/generate-keys.ts`. **Never hand-edit it.** After touching either catalog, run:

```
bun run i18n:keys
```

Then commit the regenerated file alongside the catalog change — they are one change, and the pre-commit hook's `tsc --noEmit` will fail if you skip it.

## Where the locale comes from

`LocalePlugin` (`src/libs/plugins/locale.plugin.ts`, registered in `baseApp`) reads `Accept-Language` in `onRequest`, resolves it with `parseAcceptLanguage` (`src/libs/i18n/accept-language.ts` — q-value sorted, `en-GB` normalised to `en`, unsupported tags falling back to `DEFAULT_LOCALE`), and stores it via `enterLocale`. `getCurrentLocale()` (`src/libs/i18n/locale-store.ts`) reads it back out of an `AsyncLocalStorage`.

`Accept-Language` is the **only** input today. Adding a `?lang` query or `x-lang` header resolver means changing `LocalePlugin` — do not fake it at the call site.

For work that runs outside a request, wrap it with `runWithLocale(locale, fn)`. Producers handing work to a queue capture `getCurrentLocale()` and pass it in the job payload (see `AuthMailService` and `mail.md`) rather than hoping the async store survives the hop — it does not.

## Validation messages

`translateValidationMessage(err)` (`src/libs/i18n/validation.ts`) maps a TypeBox error onto the `validation.*` keys: it checks `err.schema.format` first (`email`, `uuid`, `date-time`), then pattern-matches the raw message. When you add a schema constraint whose failure it cannot classify, add both the `validation.*` key **and** the branch — do not let raw TypeBox English through.

## Don't

1. Don't write an English literal into a `ResponseToolkit.*` message, a thrown `@errors` class, or a mail subject. Use a key.
2. Don't hand-edit `keys.generated.ts`.
3. Don't add a key to `en.json` only.
4. Don't translate log messages. `log.info({ userId }, "...")` is always English — logs are read by operators, not users.
5. Don't translate internal detail: Postgres/Drizzle error codes, constraint names, stack traces, or the field and key names inside a structured error payload. Only the human-readable message string is translated.
6. **No `t()` in a repository.** A repository owns SQL (see `repositories.md`) and a message belongs
   to whoever throws — which is the **service**. `role.repository.ts`, `permission.repository.ts`, and
   the CRUD paths of `user.repository.ts` return `null` for a miss and perform no uniqueness check, so
   they have no user-facing string and do not import `@i18n`.

   The `t()` calls for existence and uniqueness live in `src/modules/settings/{role,permission,user}/service.ts`,
   attached to the throw:

   ```ts
   const role = await RoleRepository().findById(id);
   if (!role) {
   	throw new NotFoundError(t("role.notFound"));
   }
   ```

   **Two exceptions survive in `user.repository.ts`**, and neither is a business rule:
   `t("user.createFailed")` and `t("user.createRetrieveFailed")` report an `INSERT ... RETURNING` that
   came back empty — a condition only the repository can observe, so no service-side check could
   replace it. `UserInformation()` also throws `UnauthorizedError(t("user.notFound"))`, which is an
   authentication path rather than CRUD. These are not licence to add a third: if you are reaching for
   `t()` in a repository for an existence or uniqueness check, the check is in the wrong layer.

   The sibling `clean-elysia-prisma` keeps `t()` out of its repositories entirely, for the same reason.
   The two repos now agree on this.
